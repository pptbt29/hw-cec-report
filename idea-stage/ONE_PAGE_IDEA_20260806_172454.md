# RoutableKV：One-Page Research Idea

**暂定标题**：*RoutableKV: Resource-Efficient Proactive KV Lifecycle Control for SLO-Aware LLM Serving in Collaborative Edge Computing*

**论文定位**：Collaborative Edge Computing（CEC）中的多轮 LLM serving 系统；目标 venue 为 ACM/IEEE SEC，备选 ICDCS、Middleware、TCC、TPDS。

> **核心主张**：RoutableKV 不周期性重排全系统 KV，也不在请求完成后立即复制完整状态。它把长期全局 SLO-goodput 目标分解为由全局资源与节点负载信号协调的单 session 滚动决策：当某个 session 的下一轮返回风险升高时，每次只选择下一批 KV 的迁移、精确重算或等待动作；当节点预计 HBM 不足时，再按淘汰造成的全局 SLO-goodput 损失回收空闲 KV。系统作为插件叠加在现有路由器上，不重新设计请求路由策略。

## Abstract

> Collaborative edge computing pools distributed accelerators for local demand bursts. Multi-turn LLM requests remain tied to nodes holding their session KV cache. Arrival-time restoration can violate TTFT SLOs, whereas eager replication wastes scarce bandwidth, GPU time, and HBM. Consequently, idle GPUs may be unable to serve imminent requests on time. We study online KV preparation and eviction for long-run SLO-goodput under shared resources. RoutableKV estimates each completed session's return distribution and activates it near its return-risk window. A rolling controller selects each session's next migration, recomputation, or wait action using global resource and load costs. Under projected HBM pressure, nodes evict idle KV in increasing order of estimated global SLO-goodput loss. We will evaluate a router-compatible prototype on real traces, heterogeneous nodes, multiple routers, and prediction errors. We expect higher SLO-goodput per resource than reactive migration, eager prefetching, and cache-only policies.

该 Abstract 共 **10 句、141 词**，依次对应：背景、一般问题、两句动机、技术问题定义、三句方法、评估和预期结果。最后一句是待实验检验的假设，不是已有结果。

## 1. Introduction 草稿逻辑

**第 1 段——场景。** CEC 允许地理分散的边缘站点共享 GPU，以接管局部突发请求；多轮 LLM session 却携带不断增长、跨请求复用的 KV cache，因此“有空闲 GPU”不等于“能在 TTFT SLO 内接管请求”。

**第 2 段——核心矛盾。** 请求到达后再恢复 KV 可能使 TTFT 超时；请求完成后立即向多个节点复制完整 KV 又会浪费站点间带宽、后台 GPU 时间和 HBM，因为用户可能晚到或不再返回。多 session 同时准备还会相互挤压，并改变路由后的节点队列。

**第 3 段——现有工作的边界。** Llumnix 在请求运行后迁移执行状态，DualMap 在既定候选内进行到达时路由和排队请求重定向，SYMPHONY 利用 advisory 提前选择目标节点并分层预取 KV；这些工作分别证明了迁移、SLO-aware routing 和主动准备的价值，但尚未直接回答资源受限 CEC 中“何时唤醒哪个 session、下一批准备什么、其对其他请求造成多少损失、HBM 紧张时淘汰谁”的长期联合控制问题。

**第 4 段——技术挑战。** 全局联合搜索的动作空间随 session 数、节点数、KV block 和准备方式相乘；只优化某个 session 自己的达标概率又会忽略共享链路、HBM和路由队列外部影响。此外，返回时间预测存在早到、晚到和不再返回三类错误，算法不能依赖 oracle。

**第 5 段——方法。** RoutableKV 将全局受约束随机控制问题用资源与节点负载的边际损失信号分解为单 session 子问题。request 完成只登记状态并预约下一次唤醒；被唤醒的 session 使用有限时域滚动求解器，每次只执行下一批 KV迁移、精确重算或等待动作。节点侧在预计 HBM 压力出现时，从最低预计 SLO-goodput 损失的空闲 KV 开始下移或删除。

**第 6 段——贡献与验证。** 论文的主贡献是面向全局 SLO-goodput 的可扩展 KV 生命周期控制，而不是新的返回预测器、路由器或 KV传输内核。原型将接入多种宿主路由器，并在真实多轮 trace、异构节点和预测误差下，与 reactive migration、eager prefetch、cache-only policy 及离线联合 oracle 对比。

## 2. 一页技术核心

### 2.1 问题与全局目标

系统包含多个 CEC 节点、共享站点间链路和并发多轮 session。给定宿主路由器 $\rho$，RoutableKV 的长期目标是最大化单位时间内满足各自 TTFT SLO 的请求数：

$$
\max_{\pi}
\quad
\liminf_{T\rightarrow\infty}
\frac{1}{T}
\mathbb E
\left[
\sum_{r:A_r\le T}
\mathbf 1\{TTFT_r(\pi,\rho)\le D_r\}
\right].
$$

$\pi$ 是 KV准备与淘汰策略，$A_r$、$D_r$ 分别是请求到达时间和 TTFT SLO。平均后台链路与 GPU使用受预算约束；HBM 是瞬时硬容量，任何动作执行前都必须预留空间。第一版不加入公平性、请求优先级或新的 routing objective。

### 2.2 从全局问题到单 session 滚动控制

request 完成后，系统只更新该 session 的 KV版本和经验返回分布，并计算下一次唤醒时间；不立即迁移，也不扫描其他 session。返回预测是可替换输入，主实验使用严格时间切分的经验分布，advisory 仅作可选修正，oracle 只作上界。

控制面先排除模型、权限、地域和乐观 TTFT 下界均不可行的节点。对 session $s$，局部动作集合只包含基础动作：

$$
\mathcal A_s(t)
=
\{\text{等待},\ \text{向节点 }j\text{ 迁移下一批 KV},\ \text{在 }j\text{ 重算下一批 KV}\}.
$$

10 个 block 之类的批次只是执行粒度，不要求单独跨过 SLO 门槛。有限时域价值函数会判断该批次能否形成有价值的部分恢复，或能否作为到达某个 SLO 有用状态的可行步骤；若剩余批次已经来不及完成且部分准备也无益，就不启动第一批。

局部求解器每次选择：

$$
a_s^*(t)
=
\arg\max_{a\in\mathcal A_s(t)}
\left[
r_s(z_s,a)
-\boldsymbol\lambda(t)^\top\mathbf c_s(a)
-\gamma_j(t)w_s(a)
+\mathbb E[V_s(z_s')]
\right].
$$

符号说明：

| 符号 | 含义 |
|---|---|
| $z_s$、$z_s'$ | 动作前后该 session 的 KV位置、已准备 block 和返回风险状态 |
| $r_s$ | 当前动作带来的预计 SLO-goodput贡献 |
| $\mathbf c_s(a)$ | 动作消耗的链路流量、后台 GPU 时间和 HBM |
| $\boldsymbol\lambda$ | 全局资源稀缺信号；资源越紧张，对应动作代价越高 |
| $\gamma_jw_s$ | 准备使请求更可能路由到节点 $j$ 后，对其他请求造成的预计 SLO损失 |
| $V_s$ | 该 session 在有限未来时间内继续准备、等待或到达后的价值 |

理论上，在 session 转移相互独立且只通过共享资源耦合的松弛模型中，可用 Lagrangian/primal–dual 方法分解；真实系统还存在离散 block、batching、routing shift 和队列耦合，因此只声称在线近似，并与离线联合 oracle 比较最优差距。

### 2.3 事件驱动执行

```text
request完成
  → 更新该session状态与返回分布
  → 放入按下一次唤醒时间排序的定时队列

session被唤醒
  → 读取当前全局信号
  → 比较等待、迁移下一批、重算下一批
  → 只执行一个短时间片的动作
  → block完成后重新求解

真实request到达
  → 取消未执行的后台动作
  → 宿主路由器利用已完成的部分KV作最终路由
```

链路和后台 GPU通过在线“资源欠账”控制长期后台占用：连续超预算会提高后续动作代价，资源空闲则降低代价。每个准备动作还必须通过 HBM硬容量检查；未实际释放并预留空间前，不能写入新的 HBM KV。

### 2.4 HBM 压力下的独立淘汰 phase

下移和删除不属于 session 返回时的常规准备动作。节点仅在预计 HBM占用超过安全容量时启动淘汰：预计占用包括活动请求当前 KV、活动 KV短期增长、空闲 KV和已经批准但未完成的准备预留。

每个空闲 session 只登记“下一批合法尾部 KV”的淘汰候选。动作 $e$ 的排序分数为：

$$
E(e)
=
\frac{
V_s(z_s)-V_s(z_s^e)
+\lambda_B B(e)
}{M(e)},
$$

其中 $M(e)$ 是释放的 HBM，$B(e)$ 是下移流量，分子表示淘汰及其资源操作造成的预计损失；$E(e)$ 越小越先处理。分数在 request 完成、KV状态变化和返回风险跨时间桶时更新，队首执行前再次校验；不在每次报警后重算节点内所有 session。

正常压力下，系统可将低价值空闲 KV下移到 CPU内存或SSD；若活动请求马上需要 HBM 而下移来不及，则停止新的后台动作，并直接删除已有下层完整副本的低价值 HBM副本。正在 Prefill或Decode的活动 KV永不进入淘汰队列。

### 2.5 Router-compatible plugin

RoutableKV 不决定真实请求最终去哪。Router Adapter 向宿主路由器暴露各候选节点的有效 KV量、所在存储层和剩余恢复时间，并允许通过 dry-run 接口估计“假设准备这一批 KV 后，路由器会如何选节点”。因此方法可叠加在 least-loaded、cache-affinity、predicted-TTFT 或 DualMap式路由上，但不能声称对完全忽略 KV状态的任意路由器必然增益。

## 3. 预期贡献

1. **主贡献：全局目标下的可分解主动 KV 生命周期控制。** 将 CEC 中受共享链路、后台 GPU、HBM和路由队列影响的长期 SLO-goodput问题，转化为全局信号协调的事件驱动单 session 滚动控制，避免周期性联合重排全部 KV。
2. **支撑机制：SLO价值驱动的 block准备与节点回收。** 用未来价值而非即时 SLO门槛评价基础 block动作，并在 HBM压力下按单位空间的预计全局 SLO-goodput损失维护空闲 KV淘汰队列。
3. **系统贡献：可叠加在现有路由器上的端到端运行时。** 复用已有 KV迁移、重算和分层存储数据面，只新增 session定时器、局部滚动求解器、全局信号控制、节点淘汰队列和 Router Adapter。

不作为贡献的内容包括：新的 request返回预测模型、新的 request routing policy、新的 KV传输/压缩内核、公平调度和硬 SLO保证。

## 5. 实验设计

### 5.1 环境与负载

- 3–8 个异构 CEC节点，改变 GPU速度、HBM、站点间 RTT/带宽和共享链路拥塞；至少包含一个真实多机原型和一个经微基准校准的规模化 replay。
- 使用带真实 session ID和轮次时间戳的多轮 chatbot/agent trace；训练返回分布只使用历史时间段，测试严格按未来时间回放，避免 oracle泄漏。
- 主实验使用经验返回分布；额外测试 advisory、系统性早到/晚到、false return、missed return 和完美 oracle。

### 5.2 强基线与公平比较

- Arrival-time on-demand restore；
- request 完成后立即完整复制；
- 返回窗口触发的完整 prefetch；
- SYMPHONY-style advisory/single-target staging；
- reactive Llumnix-style migration；
- cache-only retention/eviction（LRU、TTL、预测复用、恢复成本）；
- “主动准备 + 独立 LRU”；
- 小规模离线联合最优 oracle。

对每个宿主路由器 $\rho$，严格比较 $\rho$ 与 $\rho+\text{RoutableKV}$，保持 trace、资源、路由参数和存储层完全一致。

### 5.3 核心 RQ 与指标

| RQ | 决定性证据 |
|---|---|
| RQ1：问题是否真实存在？ | 空闲但因 KV未就绪而无法满足 SLO 的 GPU时间比例；按需恢复造成的 SLO miss |
| RQ2：是否提高全局结果？ | SLO-goodput、P95/P99 TTFT，在相同链路/GPU/HBM预算下比较 |
| RQ3：是否更省资源？ | 后台传输字节、重算 GPU·s、准备 KV的 HBM GB·s、无效准备比例 |
| RQ4：分解与滚动控制是否必要？ | 去掉未来价值、去掉全局信号、改成周期全局扫描、改成一次性完整方案 |
| RQ5：淘汰设计是否必要？ | 最低 SLO损失队列 vs LRU/TTL/复用概率/恢复成本；正常与突发 HBM压力 |
| RQ6：是否依赖预测和路由器？ | 返回误差曲线；多种 router 的 matched-pair 增益；oracle gap |

控制面指标包括单 session 求解时间、定时器/优先队列更新开销、过期候选重算比例和前台干扰。主结果不使用 oracle预测，也不把验证本身列为研究贡献。

当前最危险的风险不是“系统做不出来”，而是各组成部分可能被审稿人视为 SYMPHONY、分层缓存、在线资源定价和价值感知淘汰的自然组合。因此开工前先做三个 kill test：

1. 在相同预测与资源预算下，RoutableKV 相对“SYMPHONY + SLO-aware target selector + LRU”的持续增益是否显著；
2. 局部滚动分解相对简单的全局优先级队列是否存在稳定 oracle gap；
3. SLO损失淘汰相对“准备策略 + LRU/恢复成本”是否确实改善端到端 SLO-goodput，而非只改善缓存指标。

若三项均无显著差距，应停止扩展系统，而不是继续增加模型或算法复杂度。
